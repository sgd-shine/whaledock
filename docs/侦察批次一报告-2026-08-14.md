# 鲸坞 WhaleDock 侦察批次一报告

- 日期：2026-08-14（America/Los_Angeles）
- 对象：`@deepseek-ai/dsh@0.1.0-rc.6`
- 范围：T1 Token 数据源、T2 任务完成事件、T3 能力查重、T4 数据规模与持续跟踪源
- 性质：只调查、不开发
- 前置依据：`AGENTS.md`、`docs/功能取舍决策-2026-08-14.md`

## 0. 先给结论

1. **S1 完成事件可行，不需要猜“日志是否安静”。** `[源码实证][运行实证]` dsh 有持久化 `turn/end`，可区分 `completed / error / aborted / blocked / max-tokens / interrupted`；Web 侧已有 `/api/events.mux` 实时流和 `/api/session.history` 断线补洞。普通对话没有独立 `taskId`，鲸坞应把 `(sessionId, turn)` 当逻辑任务、`(sessionId, seq)` 当事件唯一键。
2. **Token 看板首选薄 dsh 插件，次选本地记录读取，代理最后。** `[源码实证][运行实证]` rc.6 已有 `session/event`、`tokenUsage` projection 和持久日志；社区 `dsh-token-stats` 也是从这些服务取数，不解析 HTTP 流。插件路线实时、字段语义最接近上游，也不进入模型关键路径。
3. **现有 usage 不能冒充完整账单。** `[源码实证][运行实证]` 主模型 step 通常有 input/output/cache-read，但用户消息没有 usage、provider 可以不报、DeepSeek 不报 cache-write；标题生成等旁路模型调用存在漏计。v0.3 应标成“dsh 已观测用量”，预算熔断只能先做保守的 step 间门槛，不能承诺字节级/账单级硬限额。
4. **rc.6 的图片链路已可 REUSE，但入口并不完整。** `[源码实证]` Web 原生支持图片粘贴、整页拖放、草稿预览、持久引用、历史画廊和灯箱；没有文件选择器，也不支持普通文件。更关键的是锁定版 DeepSeek adapter 明确为 text-only，默认路由会拒绝图片；v0.4 仍需视觉 provider/插件/OCR 降级。
5. **文件读取能力存在，但 workspace 不是读取沙箱。** `[源码实证]` `read`/`read_image` 可用绝对路径和 `..` 越出 cwd，默认 `dsh-fs-sandbox` 在所有权限模式都放行读取，只限制写入。F06b 不能只靠“复制到工作区”宣称安全，必须另做 allowlist/provider 或受控解析通道。
6. **会话控制接口存在，但稳定性分层明显。** `[运行实证][源码实证]` 默认 Web 有内部 custom RPC，可创建会话、发 prompt、拉 history、订阅事件；Headless 只做一次性新会话；官方 sibling package 有 stdio JSON-RPC/ACP，但默认 CLI 未挂载。v0.4 的自动送入可短期 pin rc.6 Web RPC，不应做 DOM 自动点击。
7. **没有共享 Web 内的逐会话“临时且不落历史”。** `[运行实证][源码实证]` 空会话创建即生成 `.jsonl.zstd`，persistence seam 无 delete/retention。F10 只能降级为独立临时 `DSH_HOME`/runtime，退出后整根清理。
8. **当前数据量无读取性能压力。** `[运行实证]` 只读快照中 `~/.dsh` 为 1,372 KiB、6 个会话日志、逻辑解压 2.87 MB/5,014 行；完整扫描 usage 用时 0.05 秒。未来仍应走 projection/seq 水位增量，不应每次全量解压。

## T1 · Token 数据源

### T1.1 会话/用量存在哪里、格式是什么

**结论：是，默认存在 `$DSH_HOME/sessions`；格式为每会话 append-only 的逻辑 JSONL，物理文件默认是多帧 Zstandard。** `[源码实证][运行实证]`

`DSH_HOME` 优先级：显式配置 → 环境变量 `DSH_HOME` → `~/.dsh`。

```text
$DSH_HOME/sessions/
  --<normalized-cwd>--/
    <encoded-session-id>/
      session.jsonl.zstd
```

- 第一条逻辑记录是 `SessionHeader`；后续是带单调 `seq` 与 epoch-ms `time` 的 `SessionEvent`。
- 文件不是可直接 `tail -f` 的逐行文本；可能含 packed chunk rows、多 zstd frame 和未 flush 尾部。
- 原始日志是权威；Web 还会写派生缓存 `$DSH_HOME/storages/session_projcache.json`。
- projection cache 可滞后、可丢弃，记录 `{ver, seq, val}` 水位，不应当作唯一事实源。

### T1.2 字段样例与“每条消息是否完整”

隔离 fake provider 返回：`prompt_tokens=10`、cache hit `3`、cache miss `7`、completion `2`。dsh 实际落盘的脱敏逻辑事件为：

```json
{"type":"assistant/chunk","seq":16,"data":{"turn":1,"step":1,"chunk":{"type":"usage","usage":{"inputTokens":7,"outputTokens":2,"cacheReadTokens":3}}}}
{"type":"assistant/message","seq":18,"data":{"turn":1,"step":1,"message":{"role":"assistant","content":[{"type":"text","text":"hello"}],"source":{"kind":"model","provider":"deepseek-official","model":"deepseek-v4-flash"},"id":"<message-id>"},"usage":{"inputTokens":7,"outputTokens":2,"cacheReadTokens":3}}}
{"type":"turn/end","seq":20,"data":{"turn":1,"reason":{"kind":"completed"}}}
```

`TokenUsage` 契约：

```ts
{
  inputTokens: number;       // 未缓存 input，不是 provider prompt_tokens 总数
  outputTokens: number;
  cacheReadTokens?: number;
  cacheWriteTokens?: number;
  reasoningTokens?: number;  // 已包含在 outputTokens，不能重复相加
}
```

**“每条消息都有 input/output/cache token”结论：否，只有部分。** `[源码实证][运行实证]`

- `user/message` 没有 usage。
- `assistant/message.data.usage` 可选；provider 不报就不存在。
- 流式过程中可能先有 `assistant/chunk {type:"usage"}`；失败请求也可能只有 usage chunk，没有最终 assistant message。
- token-meter 以同一 `turn + step` 的最终 assistant usage 替换前面的 chunk usage，避免重复计数。
- DeepSeek adapter 把 `prompt_tokens - cached_tokens` 映射为 `inputTokens`，cache hit 映射为 `cacheReadTokens`。
- DeepSeek rc.6 adapter 不提供 cache-write metric；projection 中的 `cacheWriteTokens: 0` 是聚合层补零，不是 provider 明确返回零。

关键源码：

- `$RC6_ROOT/@deepseek-ai/dsh-llm/lib/types/types.d.ts:115-129,267-297`
- `$RC6_ROOT/@deepseek-ai/dsh-llm-deepseek/lib/index.js:183-198`

### T1.3 预算看板的关键漏计风险

**结论：本地事件能覆盖主 Agent step，但不是完整 provider 账单。** `[运行实证][源码实证]`

一次成功的隔离 `hello` 实验中，本机 stub 实际看到：

```text
POST /chat/completions
POST /chat/completions
```

会话日志只出现一组主 step usage，同时出现 `session/title-llm-request`，没有标题模型调用的 usage。也就是说，标题生成是第二次 provider 请求，但没有进入 `tokenUsage` 总计。包内 token-meter 文档还说明，compaction 直接调用 `ctx.llm.stream` 的路径也不自动报告 usage。

**对功能的含义：** `[推断]`

- Token 看板名称/说明必须是“dsh 已观测用量”，不可标为“账单”或“精确费用”。
- reasoning token 已在 output 中，不得双计。
- 熔断只能在收到 usage 后阻止下一 step/下一 turn；DeepSeek usage 位于流尾，当前请求的大部分成本已经发生。
- v0.3 可用保守阈值和明确误差提示；若产品将来承诺 provider 账单级硬限额，需另接 provider quota/billing，或重新评估全流量代理。

### T1.7 三条路线推荐排序

#### 1. 薄 Cordis 插件（推荐）

`[源码实证][推断]` 使用 `session/event`、`sessionProjections.onChanged()`，需要时结合 `jobs.onJobDone()`；向鲸坞只暴露过滤后的聚合数字和状态。优点是实时、不解压、不进入 provider 请求链，且与官方 token-meter/社区插件同路。前提是锁 rc.6、完成插件打包与许可门槛、做 contract smoke。

#### 2. 本地记录读取（降级/离线）

`[源码实证][推断]` 外部 sidecar 应尽量调用官方 `sessionPersistence.readFrom()`，不应自己 `tail` 压缩文件。直接文件读取会接触完整用户内容，且要处理 zstd 多 frame、packed rows、flush 尾部和 rc 格式漂移。适合离线导入或插件不可装时的只读降级，不适合实时主路线。

#### 3. 本地 API proxy（最后）

`[运行实证][推断]` 技术前提成立，但代理会接触全部 prompt/response，成为单点故障，还必须重放所有流式/tool/retry/error 语义。它唯一明显优势是有机会覆盖标题生成等旁路请求；在 rc.6 已产出主 step usage 的前提下，不值得为 v0.3 统计引入。

## T2 · 任务完成事件（S1）

### T2.1 回答完成/任务完成怎样表达

**结论：一次对话 turn 有正式终态；“更大范围用户目标”只部分可由它代表。** `[源码实证][运行实证]`

| dsh 终态 | 结构化表达 | 鲸坞状态 | 是否报成功 |
|---|---|---|---|
| 正常回答完成 | `turn/end.data.reason.kind === "completed"` | `completed` | 是，但建议该 turn 至少有一个 `assistant/message` |
| 报错 | `kind === "error"`，带 `LlmFailure` | `error` | 否 |
| 取消 | `kind === "aborted"`，cause=`user/parent/hook/disposed/legacy` | `cancelled` | 否 |
| 策略阻断 | `kind === "blocked"` | `blocked` | 否；不是等待人工 |
| 输出上限 | `kind === "max-tokens"` | `incomplete/max-tokens` | 否 |
| 崩溃恢复 | `kind === "interrupted"` | `interrupted` | 否 |
| 等待人工 | 实时 `approval/requested` 或 `question/requested`，直到 resolved | `waiting-human` | 瞬态，不是 turn 终态 |

隔离成功/错误/强制取消三组结果：

```text
success: turn/end reason=completed
error:   turn/end reason=error
cancel:  进程 SIGINT 后物理尾部暂时没有 turn/end
```

源码的 repair 逻辑在下次 inspect/load 时为开放 turn 合成 `step/end` 与 `turn/end reason=interrupted`。真实目录的脱敏聚合也观测到 `2 completed + 1 interrupted`，与恢复契约一致。`[源码实证][运行实证]`

关键源码：

- `$RC6_ROOT/@deepseek-ai/dsh-session/lib/types/types.d.ts:135-169,223-312,420-452`
- `$RC6_ROOT/@deepseek-ai/dsh-agent-loop/lib/index.js:515-664`
- `$RC6_ROOT/@deepseek-ai/dsh-session/lib/index.js:606-724`

`assistant/message` 只表示一次模型响应组装完成；它后面仍可能有 tool call 和下一 step。正式终态必须看 `turn/end`。若后台 jobs 仍为 `running/stopping`，只能说“前台回答完成”，后台任务要按 Job ID 单独结算。`[源码实证][推断]`

### T2.2 事件层接入路线

#### 路线 A：dsh 内部插件

`[源码实证]` `ctx.on('session/event', ...)` 收到提交后的正式原始事件。恢复 seed 历史不会重新触发 live listener，插件必须持久化游标或在启动时补读 history。

#### 路线 B：当前 Web/API（v0.3 可用）

`[源码实证]` `/api/events.mux` WebSocket 会推：

```text
session/event { sessionId, event }
session/subscribed { sessionId, lastSeq }
approval/requested | approval/resolved
question/requested | question/resolved
```

### T2.4 等待人工的准确边界

**结论：实时可准确区分；进程重启后不能恢复为可回答的 pending。** `[源码实证]`

实时规则：

1. `approval/requested`：按 `approvalId` 加入 pending；同 ID 的 `approval/resolved` 移除。
2. `question/requested`：按外层 `rpcId` 加入 pending；`question/resolved.questionRpcId` 移除。
3. pending map 非空即 `waiting-human`；此时 Agent 仍可能是 `running`。
4. 同一 dsh 进程内 WebSocket 重连，未解决请求会重放。

重启限制：

- dsh 进程重启会丢 pending question/approval 内存表。
- approval 日志有 `approval/asked` 与 `approval/decided`；unmatched 只能说明“曾等待/已中断”。
- question 没有独立持久审计事件；只能从 `ask_user_question` tool call 缺 matching result 推测，不能恢复成可交互 waiting 状态。
- `blocked` 是 pre-step 拒绝，不是 waiting-human。

### T2.5 重启恢复与耐久性

**结论：终态和会话历史可恢复；运行中状态、pending、普通后台 Job 不可恢复。** `[源码实证][文档声明]`

| 对象 | 重启后 |
|---|---|
| 已落盘 `completed/error/aborted/...` | history 可恢复 |
| 崩溃开放 turn | inspect 给平衡视图；load/resume 提交 `interrupted` 修复 |
| waiting question/approval | 不能恢复成可回答 pending，只能标曾等待/已中断 |
| 本地后台 Job | 进程内对象，退出即丢 |
| Workflow | 完成记录可持久化，执行本身不 journaling/resume |

耐久性窗口：`session/event` 是内存提交后的正式事件，但 JSONL 默认最多按约 200ms 批量写入，`turn/end` 后没有专门立即 flush。硬崩溃落在此窗口，刚看到的 `completed` 可能重启后成为 `interrupted`。`[源码实证]`

**对功能的含义：** `[推断]`

- 插件路线可在通知前调用 `sessions.flush(session)`；外部 Web 路线要承认短窗口，或延迟通知并用 persistence/history 确认。
- WhaleDock 必须有独立通知去重账本。若优先“绝不重复”，先持久化 dedupe 再调系统通知，接受极端崩溃窗口可能漏一次。

证据：

- `$RC6_ROOT/@deepseek-ai/dsh-session-persistence-jsonl/README.md:22-52`
- `$RC6_ROOT/@deepseek-ai/dsh-session/lib/types/index.d.ts:373-385`

### T2.6 推荐事件状态机

最少持久字段：

```text
lastContiguousSeq

  turn,
  startSeq,
  hasAssistantMessage,
  hasDirectUserMessage
```

处理规则：`[推断]`

1. `turn/start` 建立 openTurn；`assistant/message` 标记有正式回答。
2. requested/resolved 维护 waiting-human pending map。
3. `turn/end completed` 且有 assistant message 才成为成功通知候选；其他 reason 保持独立失败/取消/不完整状态。
4. 过滤 `origin === "subagent"`，避免内部子 Agent 每回合弹通知。
5. `session/jobs` 仍有 `running/stopping` 时，只结算前台回答；Job 完成另按 Job ID。
6. `todo/write.status=completed` 只是模型 todo 快照，不是任务终态。
7. 首次启用时把既有 history 设为 baseline，不补发旧通知。

重连规则：`events.mux` v1 的 `since` 被明确忽略；重连必须先缓存实时事件，再拉 history，以 `(sessionId, seq)` 合并并只推进连续水位。若出现 gap，暂停通知、用 `beforeSeq` 分页补洞。

### T2.7 文件轮询降级规则

本批次已经证明 API/插件路线存在，因此**不建议把本地轮询作为主路线**。若未来接口失效，只能降级时：`[推断]`

1. 用官方 persistence `inspect/readFrom` 解码，不直接 `tail` `.zstd`。
2. 每 session 保存 `lastSeq`；`turn/start` 开启，`turn/end` 关闭。
3. 只有 `reason.kind=completed` 算成功；`error/aborted/blocked/max-tokens/interrupted` 分开处理。
4. unmatched `approval/asked` 只能标“可能等待”；unmatched `ask_user_question` 更弱，不能对用户断言正在等待。
5. dsh 仍活跃时，开放尾部只能标 `running/unknown`；进程重启并完成 repair 后才标 `interrupted`。
6. 持久化 `(sessionId, turn, terminalSeq)`，防止鲸坞重启后重报。

### T4.3 看板读取性能判断

**结论：当前规模不用担心，但产品实现仍应增量化。** `[运行实证][推断]`

- 当前全量扫描 0.05 秒，绝对量小。

- 不应由鲸坞直接修改、截断或清理 dsh 日志/attachment objects。
