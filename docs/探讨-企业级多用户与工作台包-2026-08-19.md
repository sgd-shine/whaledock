# 探讨：把鲸坞做成「企业自己的智能体」的客户端

日期：2026-08-19 · **状态：探讨稿，不是开发方案，不进 v0.6 / v0.7 排期**
起因：SGD 2026-08-19 提出的设想——远程控制 + 多账号登录，多个员工共享同一台设备上的 Harness，
共享智能体配置与记忆，最终面向企业级多用户；"就像现在 FDE 这个岗位在干的事，
但我们要从智能体产品本身，去为企业定制属于他们的、以 Harness 为底座的智能体"。

---

## 0. 先直接回答：我明白你的意思，而且我认为你说对了一半，另一半方向要调

**说对的那一半**（而且比你自己讲的更重要）：

> **工作台包，就是 FDE 交付物的产品化形态。**

FDE 今天在企业里做的事，本质是：把一个行业的做事方法，翻译成一套 AI 能执行的配置、提示词、
文件结构和规则，然后留在客户那儿。这件事今天**没有交付格式**——交付物是几十页文档、
一堆散落的提示词、和一个工程师的脑子。人走了就散了。

**工作台包正好就是那个格式。** 一个包 = 一套行业做事方法 = 可安装、可版本化、可审计、可复制。
你在 v0.6 已经在做的事，和你今天想到的企业设想，**不是两件事，是同一条线的两端**。
这一点你自己可能还没完全意识到——所以 v0.6 不用改方向，它就是地基。

**方向要调的那一半**：

> **「多个员工共用一台设备上的同一个 dsh」这个具体形态，今天在技术上是不安全的，
> 而且这个坑不是我们能填的。**

不是难做，是**做出来就是错的**。下面第 2 节详细说为什么。
正确的形状是：**共享内容，不共享进程。**

---

## 1. 侦察结论：有没有人在做？有，而且不少

2026-08-19 现场检索。生态里已有约 **1,472 个 dsh 插件**（awesome-dsh-plugin 收录数）。
你想到的每一块，都已经有人在做了：

### 1.1 多租户网关（跟你的设想最接近的）

**`slywalker2006/dsh-passwords`** ★14 —— 自我描述就是
「把 DeepSeek Harness 变成多租户平台：远程访问 + 自动 HTTPS、子用户权限与配额、
沙箱强制、加密认证、审计日志」。

它已经做到的：

| 能力 | 细节 |
| --- | --- |
| 账号体系 | 1 个管理员 + 无限子用户，各自独立凭证，全在 dsh 设置界面里管，不用 SSH |
| 工作区白名单 | 子用户只能进指定文件夹 |
| 会话隔离 | 子用户只看得到自己的会话 |
| 沙箱分级 | 只读 / 只能写工作区 / 完全放开，三档 |
| 配额 | 每小时 token 上限、每天时长上限，超了直接拒绝 |
| 提权拦截 | 子用户的 AI 想要更高权限时，网关直接把审批变成"拒绝" |
| 安全工程 | bcrypt、JWT、指数退避锁定、IP 限流、Let's Encrypt 自动 HTTPS、证书拿不到就拒绝启动（不降级明文） |
| 审计 | 每次登录/失败都有加密记录，一条命令查 |

**关键一点，也是它的天花板**：所有用户连的是**同一个 dsh 实例**。
网关管的是"谁能进来"，不是"进来之后各跑各的"。**agent 配置与记忆在实例层面是共享的。**

### 1.2 认证与权限（更细的切片）

| 项目 | 做什么 |
| --- | --- |
| `Yuuz12/dsh-webui-auth` | 在 HTTP/传输层强制 Web UI 认证 + 服务端会话 |
| `PerryLink/dsh-permission-rules` | 声明式权限规则，按工具名和工作区路径匹配，带审计日志 |

### 1.3 远程访问（这块已经很卷）

| 项目 | 做什么 |
| --- | --- |
| `JUANWANG-BUAA/dsh-full-remote` | 服务端 API 访问、按设备分会话、可选审批 |
| `liguobao/deepseek-harness-remote` | 多设备远程，**Noise IK 端到端加密** |
| `Blank-not-black/dsh-Remote` | 手机远程控制，LAN/Tailscale 网关，安卓 App，文件传输 |
| `shaobeichen/dsh-pocket` | 手机远程 + 实时同步 + 移动端自适应 |

> **结论：远程这一块不要碰。** 至少四个项目在做，有的已经上端到端加密和安卓客户端。
> 这是纯功能竞赛，我们没有优势，进去就是被卷。这也顺手确认了 v0.7 的"扫码远程"要重新评估。

### 1.4 共享记忆（这块有真东西）

**`csyangwen/dsh-memory-evolve`** ★63 —— 跨会话长期记忆 + 后台自我进化。
五轨记忆（用户画像 / 全局事实 / 项目关键记忆 / 日志 / 技能库），**用 git 存**，
按项目分支隔离，**支持配一个共享记忆仓库让团队同步**，全局记忆默认留本地。
写入要用户确认才落盘。

> 这个设计非常聪明：**用 git 做记忆的多人同步**，天然有版本、有 diff、有权限（就是仓库权限）、
> 有审计（就是 commit log），一行服务端代码都不用写。
> **你说的"共享记忆"，最靠谱的实现方式已经被人找到了，而且是对的。**

### 1.5 多智能体协作

`NanmiCoder/dsh-agent-teams`、`toolclub/dsh-agent-team-gui`（设置里配持久多模型小队）、
`whyihaveyou/dsh-suite` 的 team-board（基于 Cordis service key 的共享任务板）。
注意：这些是**多个 agent** 协作，不是**多个人**协作，跟你说的不是一件事。

### 1.6 桌面壳里，没有人做多用户

头部两家（anywhere-labs 1.33 万★、dataelement）都是**单人单机**的壳。
**"桌面客户端 + 企业多用户"这个交叉点，目前是空的。**
但空着不一定是机会，也可能是因为它不该在桌面壳里做——见第 2 节。

## 2. 必须先说清的坏消息：今天的 dsh 不是一个多用户系统

这一节是整篇里最重要的。**如果这几条你不认同，后面的所有设计都不用看了。**

### 2.1 上游自己就没有认证

`AcidGr/dsh-web-lan-access` 这个让 Web UI 能被局域网访问的插件，文档里原话是：

> 绑定 `0.0.0.0` 意味着**同一网络里的任何人都能不经认证访问这个 agent**。
> 在有公网 IP 的服务器上，这意味着整个互联网。

而且它明确指出：`settings.*`、`credentials.*`、`llm.discoverModels`
这些方法**被官方钉死在 loopback**，怎么配都不给远程调。

> **官方用"钉死在本机"这个动作，替代了"做一套权限系统"。**
> 这不是疏忽，这是一个产品判断：dsh 假设"用它的人 = 这台机器的主人"。
> 所有多用户方案，都是在跟这个假设对抗。

### 2.2 插件在进程内全权限运行

第三阶段方案第 2 节已经查证过：插件是 pnpm 装进 profile，在 harness 进程内**全权限**运行，
官方沙箱只管子进程，不管插件自身。第三方评测原话：
「plugin trust currently relies on good faith rather than technical isolation」。

Wavect 的企业就绪度评测把话说得更死：

> 沙箱管的是**文件系统效果**。**网络访问和进程可见性根本不在这套词汇表里。**
> dsh「还不是一个你可以凭势头就采用的生产控制面」，仍是 developer preview，明写有破坏性变更。

它给企业开的必做清单是：网络出口策略、独立的短期凭证、插件版本钉死与依赖清单、
敏感动作强制人工审批、追踪留存以便审计。**每一条都是"你自己在外面加"，不是 dsh 提供的。**

### 2.3 所以"多个员工共用一个 dsh"到底意味着什么

```
      员工 A ─┐
      员工 B ─┼─→ [ 网关：认证/配额/权限 ] ─→ [ 一个 dsh 进程 ]
      员工 C ─┘                                  │
                                                 ├ 一套 API 密钥
                                                 ├ 一套插件（进程内全权限）
                                                 ├ 一套记忆
                                                 └ 一个操作系统身份

      网关能拦住的：谁能进这扇门
      网关拦不住的：门里面的一切
```

**共用一个 dsh = 共用一个身份、一套密钥、一个爆炸半径。**

- 员工 A 装的一个插件，能读到员工 B 的会话、密钥和文件——因为它们在同一个进程里。
- 谁调用了模型、花了谁的 token，日志里能分清；但"是谁让 agent 删了那个文件"，
  从操作系统角度看**全都是同一个人干的**。
- 出事之后没法做责任认定。企业最在意的恰恰是这个。

`dsh-passwords` 那种网关是**在外面加了一把很好的锁**，
但它锁不住**里面**。这不是那个项目做得不好——**这是架构层面就锁不住。**

### 2.4 那正确的形状是什么

> **共享内容，不共享进程。**

把三件事拆开，分别解决：

| 层 | 问题 | 正确做法 | 谁来做 |
| --- | --- | --- | --- |
| **谁能进** | 认证、网络暴露 | 反向代理 / Tailscale / 网关插件 | 已经有人做了（dsh-passwords / dsh-webui-auth），**不该是我们** |
| **谁在跑** | 隔离、责任认定 | **每个人一个独立 agent 实例**，靠操作系统用户或容器隔离 | 企业 IT / 我们可以做调度 |
| **共享什么** | 方法、记忆、规则 | **工作台包 + git 记忆仓库 + 权限规则文件** | ✅ **这才是我们该做的** |

隔离等级，从危险到安全：

| 等级 | 形态 | 隔离强度 | 评价 |
| --- | --- | --- | --- |
| L0 | 多人连同一个 dsh 实例 | 只有网关那一层 | ❌ 不要做。责任认定不成立 |
| L1 | 一台机器，每人一个操作系统账号，各跑各的 dsh | 操作系统级 | ⭕ **可以做，而且老实**。这是"共享一台设备"唯一正确的解法 |
| L2 | 一台机器，每人一个容器 | 容器级 | ✅ 更好，但运维成本上一个台阶 |
| L3 | 每人一台机器 / 一个云实例 | 完全 | ✅ 最安全，也是今天绝大多数企业实际会选的 |

**你说的"共享同一台设备"，如果一定要做，正确形态是 L1 而不是 L0。**
而 L1 其实不需要我们做什么特别的——它就是"每个员工用自己的系统账号登录这台机器"，
鲸坞在每个账号里各跑一份，配置各自独立，**共享的是那个包和那个记忆仓库**。

## 3. 三种可能的产品形态，按"离我们现在有多近"排序

### 形态一：企业工作台包（最近，而且我们已经在做了）

**痛点一句话**
> 我们公司有一套自己的做事方法，新人要学三个月。AI 来了也一样，每个人都在从零调教它。

**普通用户（企业员工）怎么用**
1. IT 在内网发一个文件夹：`XX公司-合同初审台`。
2. 员工把它拖进鲸坞窗口，装好。
3. 切过去 —— 文件夹结构、五个按钮、审查口径、免责话术，**全公司统一**。
4. 公司改了口径，IT 发新版包，员工再拖一次覆盖。

**示意**
```
  公司的 know-how              可交付物              员工机器
  ─────────────              ─────────            ─────────
  法务的审查清单     ──┐
  历史判例的口径     ──┼──→  📦 合同初审台 v3  ──→  拖进鲸坞 → 装好
  免责话术模板       ──┤       （只有数据）
  文件归档规范       ──┘                            全公司同一套
```

**为什么这是最真的一条**：它不需要任何新的技术，v0.6 的机制原样就能用。
**FDE 交付的东西，第一次有了一个可以拿在手里的文件格式。**

---

### 形态二：接上企业的共享记忆库

**痛点一句话**
> 老王调教了半年的 AI 特别懂我们业务，但那些经验全在老王电脑里，他离职就没了。

**怎么用**
1. IT 建一个私有 git 仓库当"公司记忆库"。
2. 员工在鲸坞里填一次仓库地址 → 接上。
3. AI 学到的公司级知识（口径、术语、踩过的坑）**提交进去要人工确认**，
   个人的东西默认留本地不上传。
4. 新人第一天就能用上公司三年积累的记忆。

**示意**
```
  员工A ──┐                        ┌── 个人记忆（本地，不上传）
  员工B ──┼── 公司记忆库(git) ──┤
  员工C ──┘   有版本/有diff/     └── 公司记忆（要人工确认才提交）
              有权限/有审计
```

**关键判断**：`dsh-memory-evolve`（★63）已经把这条路走通了，而且**用 git 是对的**。
我们不该重做一个，**我们该做的是"在坞里一键接上，并且让每条记忆看得见来源"**——
谁提交的、什么时候、基于哪次对话。企业要的是这个可追溯性，不是记忆本身。

---

### 形态三：一台设备多员工（你原始的设想，最远、最危险）

**痛点一句话**
> 公司买了一台带好显卡的机器跑本地模型，总不能只给一个人用。

**能做，但只能是这个形态（L1）**
```
     一台带显卡的机器
     ├── 系统账号 employee_a → 自己的鲸坞 + 自己的 dsh + 自己的密钥
     ├── 系统账号 employee_b → 自己的鲸坞 + 自己的 dsh + 自己的密钥
     └── 系统账号 employee_c → 自己的鲸坞 + 自己的 dsh + 自己的密钥
                    ↓ 三个人共享的只有这些 ↓
         · 本地模型服务（各自调，各自计费）
         · 工作台包（IT 放在公共目录，各自装）
         · 公司记忆库（git，各自拉）
```

**注意这里我们其实什么都不用新做**——操作系统本来就是这么工作的。
真要说有什么可做：
- 让工作台包能从一个**只读的公共目录**被发现（现在只扫两个根，加第三个根，很小的改动）
- 显示"这台机器上还有谁在跑任务"，避免三个人同时压爆一张显卡（这个有点意思，但不急）

**我的判断：这个形态不值得作为一条产品线去做。**
它的价值在"共享算力"，而共享算力是模型服务层的事（Ollama / vLLM 那一层），不是桌面壳的事。

## 4. 那鲸坞在这盘棋里凭什么是那个客户端

诚实地列一遍我们**不该**去抢的和**该**去占的：

| 不该做 | 为什么 |
| --- | --- |
| 认证网关 | 已经有 dsh-passwords 等在做，而且这是安全责任最重的一层。做砸了是事故，做好了也没人记得 |
| 远程访问 | 至少四个项目，有的已上端到端加密 + 安卓客户端。纯功能竞赛，我们必输 |
| 记忆系统 | dsh-memory-evolve 已经把 git 这条正确的路走通了 |
| 沙箱 / 隔离 | 这是操作系统和容器的事，桌面壳做不了也不该做 |

| 该做 | 为什么只有我们能做 |
| --- | --- |
| **包的分发与管控** | 企业 IT 真正要的不是"员工能用 AI"，是"**我知道员工装了什么**"。装包前的清单、许可证、它会碰哪些路径、它推荐装哪些第三方 skill——**这套东西我们已经有了**（THIRD_PARTY_NOTICES 逐包清单、发布审批门、绝不执行包内代码）。生态里没有第二家有 |
| **原生外壳** | 员工不用开着浏览器；托盘知道 agent 卡在哪；这是 20 多只 Web 内嵌桌宠做不到的 |
| **组织策略** | 见下 |

### 一个我认为真正值钱的新概念：组织策略文件

企业 IT 要的其实是 MDM（设备管理）那一套的最小版本：

```
  公司发的一个 policy.json（只读，放在员工管不到的位置）
  ├── 只允许装这几个来源的工作台包
  ├── 禁止任何包把工作区指向这些路径（财务目录、人事目录…）
  ├── 这些动作必须人工确认，不许 agent 自己拍板
  └── 每次装包/切工作台，写一行本地审计日志
```

**这是企业会付钱的东西，而且它跟我们已有的安全链是同一套东西的延伸，不是新方向。**
但它同时也是我们第一次真正"面向企业"——一旦沾上，就有了长期义务（见第 6 节）。

## 5. 关于 FDE 这个类比：哪里成立，哪里不成立

**成立的部分**：FDE 的产出物第一次有了一个可交付的格式。可安装、可版本化、可审计、可复制。
这解决的是 FDE 行业最大的痛点——**知识随人走**。

**不成立的部分**，而且这一条很重要：

> **FDE 值钱的地方，从来不是那份交付物，是"贴着客户业务把问题问清楚"的那个过程。**
> 那部分不可能被一个包替代，也不该被替代。

所以：

- 我们**不卖 know-how**（你说得对，我们没有）。
- 我们卖的是**载体和管控**：让别人的 know-how 能被打包、被分发、被验证、被审计。
- **谁的 know-how 谁赚钱。**

虎嗅那篇对 dsh 生态的分析里有一句话说得很准，可以直接拿来当我们的商业观：

> 「持久性来自让其他参与者真正赚到钱，而不是来自控制整个技术栈。」

这跟我们做包机制的逻辑是同一个：**底座通用稳定，把行业留给别人。**（正好是你今天说的那句话。）

## 6. 红线与风险（沾上企业之前必须想清楚的）

| # | 风险 | 说明 |
| --- | --- | --- |
| 1 | **绝不能声称安全边界** | 在"插件进程内全权限"这个前提下，我们所有的检查都只是绊线。可以说"我们的包只有数据没有代码"，**不能说"用鲸坞管起来就安全了"**。说过头会反噬，企业客户尤其 |
| 2 | **长期义务** | 企业客户要 SLA、合同、发票、安全问卷、漏洞响应时限。一个 MIT 的非官方个人项目扛不住这些。**接第一个企业客户之前，先想清楚谁来接电话** |
| 3 | **合规** | 一旦碰审计日志、员工行为记录、多租户数据，就进了个人信息保护的射程。这不是技术问题 |
| 4 | **上游不稳** | dsh 仍是 preview，明写有破坏性变更，8 天发了 7 个 rc，Issues 关闭。**企业要的稳定性，上游现在给不了。**这一条要提前跟客户讲明，不能替上游背书 |
| 5 | **精力** | 我们连 v0.6 都还没开始写代码。企业形态最快也是 v0.8 以后的事 |
| 6 | **别被一个客户带跑** | 第一个企业客户会提一堆只对他有用的需求。**凡是不能表达成"通用字段"的，一律拒绝**——这正好呼应 A-13 的底座通用性原则 |

## 7. 我的建议：现在做什么

| 时间 | 做什么 | 理由 |
| --- | --- | --- |
| **现在（v0.6）** | **一个字都不用改方向**，把包机制做通用做稳 | 它本身就是企业形态的地基。A-13 那五个纸面包，建议**加一个"律师·合同初审台"当成企业场景的预演** |
| v0.7 | 包的**分发与验证**：来源、清单、许可证、它会碰哪些路径 | 这本来就是个人用户也需要的（"我装的这个包安全吗"），顺手就是企业要的 |
| v0.8+ | **组织策略文件** + **一键接企业记忆库** | 到这一步才算真正面向企业 |
| 不做 | 认证网关、远程访问、记忆系统本体 | 已经卷了，或者不该我们做 |
| 不做 | L0 式"多人连同一个 dsh" | 架构上就是错的 |

### 但是，比上面所有排期都重要的一件事

> **去找一个真实的企业聊一次，再决定要不要做这条线。**

我们现在讨论的全部内容——包括我上面写的每一条——**都是从技术侧往外推的，没有一个真实客户在场**。
企业到底是不是这么想的，只有他们能回答：

- 他们的 know-how 真的能被写成"几个文件夹 + 几个提示词"吗？还是根本没法脱离人？
- 他们更在意"统一口径"，还是"防止员工乱用 AI"？（这两个诉求会导向完全不同的产品）
- 他们愿不愿意让 AI 碰真实业务数据？如果不愿意，前面所有设计都落不了地。
- 他们会为一个非官方开源客户端付钱吗？还是只会为"有人负责"付钱？

**一次真实对话的信息量，大过我们十份方案。** 这条线在拿到那次对话之前，
建议只当作"v0.6 要保持通用性"的动机，不当作排期项。
