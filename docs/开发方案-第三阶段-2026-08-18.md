# 鲸坞 WhaleDock 第三阶段开发方案

日期：2026-08-18 · 起点版本 v0.5.0（已发布）· 本方案覆盖 v0.5.1 → v0.6 → v0.7

---

## 0. 这一版方案为什么要重写

两件事同时发生：

1. **一个日本用户在 M5 Mac 上打不开 v0.5.0**，提示「文件已损坏，应移到废纸篓」。查下来是**分发级缺陷**，不是个例——所有从 GitHub 下载 v0.5.0 的 Apple Silicon 用户都会遇到（详见第 1 节）。
2. **重新扫了一遍 dsh 开源生态**，发现格局在 8 天里已经完全变了（详见第 2 节）。上一版方案里"做一个好用的桌面壳"这个定位，现在**已经不成立**。

所以这一版不是在原路线上加功能，是先止血，再换赛道。

## 1. v0.5.1：把「已损坏」修掉（已完成，待发布）

### 1.1 根因

不是文件下载坏了，也不是 M5 芯片不兼容。链条是这样的：

1. `package.json` 与 `release.yml` 里设了 `CSC_IDENTITY_AUTO_DISCOVERY=false`，让 electron-builder **完全跳过代码签名**；
2. electron-builder 打包时会重写 `Info.plist`、重命名主可执行文件、注入 `app.asar`，Electron 官方预编译包自带的签名因此失效；
3. 跳过签名 = 产物里**根本没有 `Contents/_CodeSignature/CodeResources`**（已实测核对 v0.5.0 的 arm64 裸包，确实缺这个目录）；
4. 本机构建、本机打开没问题，因为本地文件没有隔离属性；
5. 但**从 GitHub 下载**的文件会被 macOS 打上 `com.apple.quarantine`，此时 Gatekeeper 会校验包级签名——校验失败，Apple Silicon 上直接判「已损坏」；
6. 更糟的是，这条提示**用「右键 → 打开」绕不过去**（那条路只对"签了名但没公证"的 App 有效，且 macOS 15 起 Apple 已移除该入口）。

一句话：**我们发的是一个在 Apple Silicon 上物理上打不开的包，而且用户没有自救路径。**

### 1.2 修法

| 改动 | 文件 | 作用 |
| --- | --- | --- |
| 新增签名器 | `scripts/macos-codesign.js` | 挂在 electron-builder 的 `afterPack` 上，按「单体 Mach-O → 嵌套 bundle → 外层 .app」顺序逐个 `codesign`，默认 ad-hoc（无证书、无费用、不联网） |
| 新增 entitlements | `build/entitlements.mac.plist` | 为将来的 Hardened Runtime 备好（allow-jit / 内置引擎 dlopen 第三方 .node 所需的 library-validation 放行） |
| 打包配置 | `package.json` | `afterPack` 钩子；`mac.identity: null` 让 electron-builder 一律不插手签名，避免两条路径打架；版本 → `0.5.1` |
| 发布流水线 | `.github/workflows/release.yml` | ①可选导入 Developer ID 证书（有 secret 才走）②构建后**解压 zip 复验签名，不合格直接让发布失败** ③可选公证 + staple（有 secret 才走）④Release 说明改写 |
| 用户文档 | `README.md` + `docs/macOS-安装与已损坏提示.md` | 删掉过时的「右键 → 打开」，改成系统设置路径；新增中/英/日三语说明，可整段转发 |
| 回归测试 | `test/macos-codesign-smoke.js` + `test/smoke.js` | 新增 19 项直测 + 2 项打包合约；缺包级签名必须 fail-closed |

`npm run smoke` 已回读 **ALL PASS**。

### 1.3 修完之后用户看到什么

| 版本 | 下载后双击 |
| --- | --- |
| v0.5.0 | ❌「已损坏，应移到废纸篓」，无自救路径 |
| **v0.5.1** | ⚠️「无法验证开发者」→ 系统设置 → 隐私与安全性 → 「仍要打开」→ 正常使用 |
| 配好苹果证书之后 | ✅ 双击直接开，零提示 |

SGD 已拍板尽快做公证。操作步骤见 [`公证接入指南-2026-08-18.md`](公证接入指南-2026-08-18.md)——
**代码已经全部预埋好，配六个 GitHub secret 即自动生效，不需要再改一行代码。**

### 1.4 v0.5.1 发布清单（含必须人工做的部分）

1. 提交并推送本次改动 → CI 三平台绿；
2. 打 `v0.5.1` tag → Release workflow 构建；
3. **新增的硬门**：mac job 会解压 zip 复验签名，签名不过直接失败；

   已经装了 v0.5.0 的用户不会自动收到修复，只能靠这条；
6. **人工补做**：给那位日本用户回一句，内容直接抄 `docs/macOS-安装与已损坏提示.md` 的日语段。

## 2. 生态重估：桌面壳这条路已经挤死了

2026-08-18 现场检索结论（完整清单与 URL 见附录 A）：

- **dsh 本体 8 天前才公开**（npm 首版 2026-08-10，公开 08-13），现在 **15 万星**，最新 `0.1.0-rc.7`（08-17）。官方 README 明写"会有破坏性变更"，**没有 1.0 路线图，Issues 关闭**。
- **桌面壳已经出现 18 个以上**。头部 [anywhere-labs/deepseek-harness-desktop](https://github.com/anywhere-labs/deepseek-harness-desktop) **1.33 万星 / 571 fork**，两天内从 v0.1 迭代到 v2.0，已捆绑 Node+dsh+pnpm、已做签名公证。第二名 [dataelement/dsh-desktop](https://github.com/dataelement/dsh-desktop) 有公司背景和独立官网。
- **桌宠也挤死了**：dsh 生态里 20+ 只鲸鱼，但**全部是 Web UI 内嵌浮窗**——关掉浏览器就没了。唯一的原生窗口实现（Rust 写的 dsh-plugin-pet-rs）连二进制都发不出来。
- **"鲸"这个意象已经红海**：whale-girl(233★)、dsh-deep-whale(1.35k★)、dsh-ui-whale、pixel-whale、whalito、whalehub……**"坞 / Dock" 才是我们没被占的那个词。**
- **官方没有做桌面端的迹象**，但也没有任何承诺。
- **插件安全是官方留的最大空洞**：插件 = pnpm 装进 profile → 在 harness 进程内全权限运行，官方沙箱只管子进程不管插件自身，第三方评测原文："plugin trust currently relies on good faith rather than technical isolation"。

### 2.1 由此得出的定位判断

**不要再跟头部拼"壳的功能多"。** 对方 1.3 万星、有公司、迭代比我们快、已经做完签名公证。功能对标是必输的仗。

鲸坞真正握在手里、别人短期抄不走的东西只有三样：

1. **原生外壳能力**——独立宠物窗、托盘、全局快捷键、截图，**不依赖浏览器开着**。生态里 20 多只桌宠没有一只做到。
2. **安全与合规链**——`THIRD_PARTY_NOTICES` 逐包清单、发布审批门、S1–S6 刹车、**「绝不执行包内代码」的声明式包模型**。整个 dsh 生态里没有第二个项目有这套东西，而这恰好对着官方最大的空洞。
3. **SGD 本人的内容生产能力**——能把每一个功能拍成视频讲清楚。这是绝大多数开源项目没有的分发渠道。

**第三阶段的全部设计，就是把这三样串成一条线。**

## 3. v0.6 主线：一个坞，停不同的船 —— 工作台包机制

### 3.1 SGD 的判断（2026-08-18）

> "Harness 是一个可以有很多种形态的智能体底座。比如我们现在做一个短视频创作的智能体工作台，
> 它第一利于视频制作和传播，第二它的用户群体的传播能力也比较强。在我们原生的常驻状态的基础上，
> 我想更多可能地去做分支，开发不同形态的智能体工作台。"

**这个判断是对的，而且正好接上了"坞"这个名字。** 但关键的工程决策是：

> **分支不是代码分支，是内容分支。一个外壳，多个「工作台包」。**

如果每种形态开一个仓库、一个 App，维护成本会指数上升，签名/合规/更新全部要乘以 N。
做成包之后，加一个新形态 = 加一个目录，不动一行外壳代码，也不新增任何发布负担。
**而且对视频素材极其友好：一期视频 = 一个工作台包。**

### 3.2 什么是「工作台包」

沿用 v0.5 宠物包/主题包已经验证过的模型，**声明式，绝不执行包内代码**（S5 铁律不放松）：

```
userData/workbenches/短视频创作台/
├── manifest.json          # 名字、图标、说明、版本、适配的 dsh 版本范围
├── theme.json             # 复用 v0.5 主题格式（可省略，省略则跟随全局主题）
├── pet/                   # 复用 v0.5 宠物包格式（可省略）
├── workspace.json         # 首次启用时要建的文件夹结构与说明文件
├── actions.json           # 侧栏/托盘上的快捷动作：按钮名 + 发给 agent 的提示词模板
├── agent.cordis.yml       # dsh 官方 agent preset 格式，交给 dsh 自己加载
├── skills.json            # 需要的 skills 清单（只列出 + 给一键复制的安装命令，绝不自动装）
└── onboarding.md          # 首次进入时显示的引导文案
```

**安全红线（继承并强化 S5）：**

- 包里**只有数据，没有可执行代码**。`actions.json` 里是提示词文本，不是脚本。
- `agent.cordis.yml` 交给 dsh 原样加载——**我们不解释、不执行它**，出错就降级到默认工作台并如实报错。
- `skills.json` **只展示、只给复制按钮，永不自动安装**。装第三方 skill 是用户的显式动作。
- 包内路径一律限制在包目录内，不允许 `..`、绝对路径、符号链接逃逸（复用宠物包已有的校验）。
- 不联网下载包。社区包走 `community-workbenches/` 目录 + PR，跟 v0.5 的宠物/主题一致。

### 3.3 第一个包：短视频创作工作台

按产品总则写：

**痛点一句话**
> 我想做短视频，但选题、脚本、口播稿、封面标题、素材清单散在五六个工具里，每次都要从零复制粘贴。

**普通用户怎么用**
1. 打开鲸坞，顶部切到「短视频创作台」；
2. 它自动在 `Documents/鲸坞工作台/短视频创作台/` 建好四个文件夹：`01_选题库`、`02_脚本`、`03_口播稿`、`04_素材清单`，每个里面有一个说明文件告诉你放什么；
3. 左边一列按钮，点哪个做哪个：
   - **「今天做什么」** → agent 读你的选题库，给三个可拍的选题和理由
   - **「写脚本」** → 选一个选题，出分镜脚本
   - **「转口播稿」** → 把脚本改成能直接对着念的口语稿（不是书面语）
   - **「出封面标题」** → 一次给 5 个，标注各自的钩子类型
   - **「列素材清单」** → 这条片子要拍/要找的画面逐条列出
4. 每一步的结果**自动落成工作区里的文件**，随时能改、能翻回去看；
5. agent 干活时，托盘的鲸鱼在摆尾；干完了冒个泡——**不用一直盯着窗口**。

**示意**
```
┌─ 鲸坞 · 短视频创作台 ────────────────────┐
│ 今天做什么 │                              │
│ 写脚本     │   （dsh Web UI 原样嵌在这里） │
│ 转口播稿   │                              │
│ 出封面标题 │                              │
│ 列素材清单 │                              │
└────────────┴──────────────────────────────┘
   托盘：🐋 摆尾中…  →  🐋 完成
```

**为什么第一个做它**：SGD 本人就是目标用户（要给鲸坞做宣传视频），能立刻自己用、自己验、自己拍。
这是最短的 dogfooding 闭环，也直接产出下一期视频素材。

### 3.4 后续候选包（先不做，列着当路线）

| 包 | 痛点一句话 | 备注 |
| --- | --- | --- |
| 文件体检台 | 电脑里几千个文件不知道哪些是重复的、哪些能删 | SGD 已实测过（179 文件/2.5GB/12 组重复发票），视频素材现成 |
| 只读审计台 | 想让 AI 看我的项目，但不敢让它改我的文件 | 直接用 dsh 的只读能力 + 鲸坞的守卫预设，是安全叙事的最佳载体 |
| 电商工作台 | 见 `project_ecom_workbench` 那条独立线 | 与这个体系天然兼容，但独立推进 |

### 3.5 原生常驻状态强化（v0.6 的另一半，SGD 已选）

工作台包让"能做什么"变多，常驻状态让"不用盯着"成立。要补的：

- **托盘状态语义化**：空闲 / 思考中 / 等你确认 / 已完成 / 出错，五态，托盘图标与宠物动作同步；
- **不开浏览器也能知道进度**：宠物窗和托盘直接读 dsh 的事件流，**不依赖 Harness 窗口是否打开**；
- **「等你确认」要能叫醒人**：agent 卡在需要确认的地方时，托盘要有明显提示（这是生态里所有 Web 内嵌桌宠都做不到的——浏览器关了就没了）；
- 集成方式**只走只读**：官方文档明示的 `dsh --profile <name> --dump-config` + HTTP/SSE 只读事件流 + 轮询兜底。**不碰 Cordis 内部 API**（第三方兼容性雷达显示只有约 14% 的插件跟得上主线，碰内部 API 的必死）。

## 4. dsh 版本跟进：先侦察，v0.5.1 不动版本锁

SGD 已拍板。侦察清单（在升 rc.7 之前必须逐条回读，任何一条不确定就不升）：

1. `0.1.0-rc.6 → rc.7` 的 **CHANGELOG / commit diff**，重点看 CLI 子命令、端口默认值、`web` 启动行为有无变化；
2. `dsh --dump-config` 的输出结构是否变了（这是我们将来集成状态的主入口）；
3. Web UI 有无破坏性改动（rc.7 新增了"插件可注册自己的设置卡片"和 Job 面板，要确认不影响嵌入）；
4. `vendor/dsh-runtime` 闭包**新增了哪些包** → 必须重跑 G1 许可证扫描，有冲突按 S1 停；
5. 包体积变化（当前安装包已接近 200 MB，再涨要评估）；
6. 用 `HARNESS_SMOKE=1 npm start` 在 rc.7 上跑一遍源码态启动；
7. 结论写成"升 / 不升 + 理由"，不升也要记下来下次从哪继续。

> 判断依据：上游 8 天发了 7 个 rc，`0.0.1-rc.3/rc.4`、`0.1.0-rc.1/rc.4/rc.5` 直接跳号缺失，官方 Issues 关闭。
> 跟版本是非官方客户端的固定成本，但**不能让它拖住"修已损坏"这件急事**。

## 6. 传播口径的调整建议

- 别再主打鲸鱼形象——`whale-girl`、`deep-whale`、`pixel-whale`、`whalito` 已经把这个意象占满了。
- 主打 **「坞」**：`一个坞，停不同的船。` 多工作台、多形态、切换即换一整套环境。
- 安全叙事是我们的第二张牌，但**话不能说过头**：在"插件在进程内全权限运行"这个前提下，
  任何静态检查都只是绊线，不是安全边界。可以说"我们的包只有数据没有代码"，
  **不能说"用鲸坞就安全了"**——说过头会反噬。
