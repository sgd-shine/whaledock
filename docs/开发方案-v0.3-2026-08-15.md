# 鲸坞 WhaleDock v0.3 开发方案

日期：2026-08-15

状态：批次 11 方案已冻结，代码尚未开始

基线：v0.2 正式发布分支当前实现；dsh 合约锁定 `0.1.0-rc.6`

依据：`docs/侦察批次一报告-2026-08-14.md` 的 T1/T2、当前源码与本地 rc.6 包源码审计

## 1. 目标与产品边界

v0.3 在不改写 Harness 主界面的前提下，为鲸坞增加一层本地、可关闭、可降级的任务事件体验：任务完成/等待人工提醒、用量与费用看板、每日软预算，以及可复制或保存的任务战报卡片。

本版本交付四个相互解耦的能力：

1. 通过 dsh `0.1.0-rc.6` 已存在的本地 HTTP/WS 接口只读观察会话事件，并在断线后用历史接口补洞。
2. 将原始 dsh 事件归一化为鲸坞中性事件，驱动任务状态机、持久去重和通知降级链。
3. 用独立的安全窗口展示今日/本周用量、任务状态、预算与价格配置，不向 Harness 页面注入任何 DOM 或脚本。
4. 从主进程持有的规范化数据生成离屏 PNG 战报，支持复制到剪贴板和保存到本地。

### 1.1 非目标

- 不修改、包装或注入 Harness Web UI；不抓取 WebView DOM，也不根据页面文案推断任务状态。
- 不给主窗口增加 preload；主窗口继续保持 `preload` 为空、`nodeIntegration:false`、`contextIsolation:true`。
- 不实现会话内容搜索、完整消息归档、远程同步或跨设备账号体系。
- 不实现精确账单。看板只展示 dsh 可观测 token 与按用户配置价格计算的估算值。
- 不主动恢复、继续、取消或修改 dsh 会话；历史接口只用于读回与补洞。
- 不承诺在进程被强杀、系统断电或上游事件尚未落盘的极短窗口内绝对不漏报。
- 不升级 dsh，不增加协议兼容猜测。若 rc.6 合约不匹配，事件层整体 fail-closed。
- 不新增运行时依赖，不引入数据库、WebSocket 第三方库、图表库、分析 SDK 或遥测。
- 不增加新的外网请求。价格不联网刷新；现有唯一批准的出站请求仍是受总开关控制的 GitHub `releases/latest` 更新检查。
- 不写入、迁移、清理或直接扫描 `~/.dsh`；鲸坞只写自己的 `userData`。

## 2. 不可放宽的硬约束

1. `lib/` 下所有模块保持纯 Node，严禁 `require('electron')`。Electron 对象、窗口、通知、托盘、剪贴板和对话框只出现在 `main.js` 与各 preload。
2. dsh 专属假设只能位于 `lib/backend.js` 与 `lib/config.js`。端口、固定版本、HTTP 路径、WS 路径、原始帧名、原始字段名与超时上限不能散落到 `lib/events.js`、UI 或测试之外的业务层。
3. `lib/events.js` 必须是协议中性的纯函数/纯 Node 编排层；它只消费 adapter 输出的中性事件和不透明 session 引用。
4. 主 Harness 窗口继续无 preload，不开启 Node，不注入 DOM。新功能只使用鲸坞自有的独立窗口及最小权限 preload。
5. 零新增 runtime dependencies；继续只使用 Node/Electron 自带的 `fetch`、`WebSocket`、`fs`、`crypto`、`EventEmitter` 等能力。
6. 不采集、上传或持久化消息正文、提示词、工具参数/结果、cwd、原始帧或裸 session ID。
7. 所有可失败功能独立降级：事件层失败不能阻断 Harness 使用，通知失败不能阻断持久化，看板失败不能杀 backend，战报失败不能污染状态。
8. 预算只能停止鲸坞本次自己拉起且仍确认归属的 backend 进程树。attach 到外部服务时绝不停止外部 dsh。
9. 每次代码改动后都运行 `npm run smoke` 并实际 `ALL PASS`；smoke、GUI 验收、打包、真机安装和线上 Release 分开取证。

## 3. 总体架构与信任边界

```text
dsh rc.6 localhost HTTP/WS
        |
        v
lib/backend.js
  dsh events adapter
  - 版本和接口 feature-detect
  - 原始帧校验、限流、限长
  - 历史读取与 WS 连接
  - 输出中性事件
        |
        v
lib/events.js
  - reconnect/history merge
  - 连续 seq 与 gap 管理
  - turn / waiting / terminal 状态机
  - usage 去重与估算
  - 持久化模型和副作用意图
        |
        v
main.js（唯一 Electron 执行层）
  - 生命周期与定时重连
  - 原子持久化调度
  - Notification / Dock / tray / banner
  - 预算 stop 授权检查
  - dashboard / report 窗口与 IPC
        |
        +--> dashboard.html <- preload-dashboard.js
        +--> notice.html    <- preload-notice.js
        +--> report-card.html <- preload-report.js（离屏）

主 Harness BrowserWindow / WebView
  - 无 preload
  - 无 DOM 注入
  - 与上述 UI 无直接 IPC
```

关键设计原则是把“知道 dsh 是什么”和“知道 Electron 是什么”分开：`backend.js` 知道 rc.6 wire contract，但不知道通知/窗口；`events.js` 知道任务语义、顺序和持久化，却不知道 `/api/...`、`session/...` 等原始名称；`main.js` 只执行经过状态机批准的副作用。

## 4. rc.6 合约与 backend adapter

### 4.1 当前已审计的只读合约

本方案只接受下列 `0.1.0-rc.6` 合约；这些事实在实现时必须以 contract fixture 锁死：

- WS 下行地址：`ws://127.0.0.1:<port>/api/events.mux`。
- WS 是 downlink-only。鲸坞不得向 socket 发送任何消息；发送会被服务端以 code `1008`、reason `downlink only` 关闭。
- WS 文本帧外壳：

  ```json
  {
    "type": "server-request",
    "rpcId": "opaque",
    "method": "session/event",
    "payload": {}
  }
  ```

- HTTP POST `/api/<method>` 请求外壳：

  ```json
  {
    "type": "client-request",
    "rpcId": "opaque",
    "method": "session.history",
    "payload": {}
  }
  ```

- HTTP 响应必须对应同一 `rpcId`，且为 `server-response`；成功结果位于 `result.ok === true` 的 `result.value`。
- 本版本只调用三个只读方法：`host.describe {}`、`session.list {}`、`session.history {sessionId,beforeSeq?,maxMessages?}`。
- `host.describe.version` 是内部 host app 版本，当前没有独立的 `protocolVersion`。2026-08-15 脱敏 live probe 已实证：实际进程是 `@deepseek-ai/dsh@0.1.0-rc.6`，但 `host.describe.version === "0.0.1"`。因此必须同时锁定根包版本 `0.1.0-rc.6`、host app 版本 `0.0.1` 和实际接口 shape；不得误拿根包版本与 `host.describe.version` 直接比较，也不得把语义版本范围当作协议兼容证据。
- `events.mux` 当前即使出现 `since` 概念也不会替客户端补历史。重连必须自己调用 `session.history` 补洞。
- `session/subscribed` 提供 `{sessionId,lastSeq}`；空会话的 `lastSeq` 为 `-1`。
- 当前可能观察到的原始帧包括 `session/event`、`approval/requested`、`approval/resolved`、`question/requested`、`question/resolved`、`session/jobs`、`session/projection`、`session/subscribed`。
- `session.list` 会返回包含 `origin:"subagent"`、`parentSessionId` 和 projection 的会话摘要；不能把它误当作只有顶层用户任务。
- rc.6 的 `session.history` 当前源码路径是 inspection/persistence 只读回读；它不持有 Agent owner，也不会因为读取而恢复冷会话或追加消息。若未来升级，必须重新做 contract probe，不能依赖旧 README 文案。

### 4.2 `lib/backend.js` 的新增边界

在现有 backend 生命周期能力旁新增一个工厂，例如 `createDshEventsAdapter(options)`。名称可在编码时微调，但职责必须固定：

- 从 `lib/config.js` 获得固定版本、loopback host、端口与超时/上限，不复制常量。
- 注入 `fetchImpl`、`WebSocketImpl`、clock 和 logger，便于纯 Node smoke；生产默认使用平台内置实现。
- 构造且只构造 loopback HTTP/WS URL；拒绝用户信息、query telemetry、重定向到非 loopback 地址和任意 host。
- 为每个 HTTP 请求生成本地随机 rpcId，校验响应 type/rpcId/result 结构，并限制响应字节数、历史页大小和超时。
- 校验 WS 只含文本、JSON 大小受限、type 为 `server-request`，然后验证 method/payload 最小结构。未知字段可忽略，未知 method 记录有界诊断后忽略；已知 method 结构错则标记合约异常。
- 绝不调用 `socket.send()`；测试应让任何 send 都立即失败。
- 将原始 session ID 映射为本进程内的不透明引用；原始 ID 只在 adapter 内用于 HTTP 请求和短期内存索引，不写日志、不进入 renderer、不落盘。
- 输出固定的中性接口：

  ```js
  {
    describe(),
    listSessions(),
    readHistory(sessionRef, options),
    subscribe({ onEvent, onStatus }),
    close()
  }
  ```

- 输出的中性事件只允许携带状态机所需字段，例如：

  ```js
  {
    kind: 'message' | 'turn-terminal' | 'approval-open' | 'approval-close' |
          'question-open' | 'question-close' | 'jobs' | 'projection' | 'subscribed',
    sessionRef,
    seq,
    observedAt,
    origin,
    parentRef,
    turn,
    step,
    messageRole,
    messageId,
    usage,
    terminalReason,
    requestRef,
    jobState
  }
  ```

中性层不需要的正文和嵌套内容必须在 adapter 校验后立即丢弃。`messageId`、`requestRef` 也只是进程内临时值；进入持久层前再次 HMAC。

### 4.3 feature-detect 与可用性状态

事件层启动时按以下顺序探测，不允许“接口报错后继续猜路径”：

1. 检查运行时是否有可注入/可用的 `fetch` 与 `WebSocket`。
2. 确认连接目标是 `127.0.0.1` 和当前 backend 端口。
3. 对鲸坞自己拉起的 backend，先确认启动 state/manifest 的根包版本为 `DSH_CONTRACT.packageVersion === "0.1.0-rc.6"`；然后调用 `host.describe`，严格校验响应外壳和 `version === DSH_CONTRACT.hostVersion === "0.0.1"`。对 attach 的外部服务，鲸坞不能凭空证明其 npm 根包版本；只能在 host 版本及下述 list/history/WS shape 全部通过后标为“外部服务已做 rc.6 合约探测”，不写成根包版本已证明。
4. 调用 `session.list`，严格校验列表最小结构。
5. 建立 WS，验证能收到合法订阅/事件帧。
6. 若已有会话，选一个会话读取一页 `session.history` 并校验 seq/分页形状；若没有会话，显示“实时接口已验证，历史补洞待首个会话验证”，首个会话出现时再完成该探测。

对外可用性只有五态：

- `probing`：正在验证，不产生完成通知。
- `backfilling`：WS 已连，正在历史补洞，实时事件只缓冲。
- `live`：历史连续且实时消费中。
- `disconnected`：已通过合约但连接暂时中断，指数退避重试。
- `unavailable`：缺少运行时能力、版本不符或合约结构不符；本次 backend generation 不再猜测，UI 诚实降级。

backend 重新拉起时生成新的 generation，再从 `probing` 开始。事件层不可用不得影响主窗口加载或 backend 的基础服务。

## 5. 历史补洞、顺序与重连

### 5.1 为什么先连 WS 再读 history

若先读历史再连 WS，二者之间的事件可能永久丢失。正确流程是：

1. 打开 WS，开始把合法实时帧放入有界内存缓冲，但不触发业务副作用。
2. 调用 `session.list` 获得会话元数据与当前范围。
3. 对每个已知会话，以持久化的 `lastContiguousSeq + 1` 为目标，通过 `session.history` 反向分页补洞。
4. 将 history 与 WS 缓冲按 `(sessionRef, seq)` 合并去重。
5. 只有从预期 seq 开始连续的数据才能推进 `lastContiguousSeq` 和状态机。
6. 完成全局连续性后切换到 `live`，再按同一规则消费后续实时帧。

`session.history` 使用 `beforeSeq` 反向分页时，adapter 负责页边界；中性层负责判断是否覆盖目标区间。若历史保留期不足、页结构异常、会话消失或 gap 始终无法关闭：

- 该会话标记 `coverage:"gap"`；
- gap 之后的 terminal、usage 和预算副作用全部暂停，不能跨洞猜测；
- 其他连续会话仍可继续；
- 看板显示“数据不完整”，不得把局部数据写成完整统计。

### 5.2 首次启用基线

首次启用不能把所有旧任务重新通知。收到 `session/subscribed.lastSeq` 后：

- 保存 `notificationFloorSeq = lastSeq`；
- `seq <= notificationFloorSeq` 的历史可用于导入用量和建立当前状态，但不发旧 terminal 通知；
- WS 已在启用后实时收到且高于 floor 的事件不能被历史导入逻辑误抑制；
- 空会话 floor 为 `-1`。

### 5.3 无 seq 请求的去重

approval/question 请求可能没有会话 seq：

- approval 用 `approvalId` 作为本次运行的稳定键；
- question requested 用外层 WS `rpcId` 作为键，resolved 用 payload 中的 `questionRpcId` 关联；
- 进入持久化前对键做本地 HMAC；
- 断线时清空 generation-scoped pending，重连后允许服务端重放重建，避免把陈旧“等待人工”无限保留。

## 6. 任务事件状态机

### 6.1 标识与核心状态

- 原始事件身份：`(sessionId, seq)`；在 adapter 外表现为 `(sessionRef, seq)`。
- 逻辑任务：`(sessionRef, turn)`。
- 完成通知身份：`(sessionRef, turn, terminalSeq)`。
- 等待人工身份：`(sessionRef, requestRef, requestKind)`。

每个会话的中性状态至少包括：

```js
{
  lastContiguousSeq,
  notificationFloorSeq,
  origin,
  openTurn: {
    turn,
    startSeq,
    startedAt,
    hasAssistantMessage,
    hasDirectUserMessage,
    usageByStep
  },
  pendingApprovals,
  pendingQuestions,
  jobs,
  lastTerminal,
  lastNotifiedTerminalSeq
}
```

状态转换必须是纯 reducer；它返回新状态与副作用意图，例如 `notify-terminal`、`notify-waiting`、`persist-critical`、`budget-crossed`，本身不调用 Electron 或文件系统。

### 6.2 terminal 映射

| 上游终止原因 | 鲸坞结果 | 通知策略 |
| --- | --- | --- |
| `completed` 且本 turn 至少有一条 assistant message | 完成 | 可发成功通知 |
| `completed` 但没有 assistant message | 未完整/未知 | 不发成功通知，保留诊断 |
| `error` | 出错 | 发失败通知 |
| `aborted` | 已取消 | 可发中性通知 |
| `blocked` | 已阻塞 | 发阻塞通知；不等同等待人工请求 |
| `max-tokens` | 未完整/达到上限 | 发警告通知 |
| `interrupted` | 已中断 | 发中性通知 |
| 未知值 | 未知 | 不猜成功，记录有界诊断 |

`session/jobs` 中仍有 `running` 或 `stopping` 只表示前台回答结束而后台 job 未清。UI 要区分“本轮回答完成”和“后台工作全部结束”，不能将前者写成所有工作结束。

### 6.3 等待人工

- pending approval 或 question 从 0 变 1 时，产生一次 `waiting-human` 意图。
- 同一稳定请求重放不重复提醒；resolved 后从 pending 删除。
- 断线清空 pending 展示；重连重放后重新确认，防止把断线前状态冒充当前状态。
- `blocked` 是 terminal 结果，approval/question 是等待输入，两者在 UI、去重键和通知文案上分开。

### 6.4 subagent 规则

`origin:"subagent"` 的会话：

- 抑制任务完成、等待人工、主窗口 banner 和未来宠物庆祝等面向用户的逐任务提醒，避免子代理风暴；
- 不排除 usage、费用和预算统计，否则委派成本会被系统性低估；
- 看板可聚合为“子代理用量”，默认不显示内容或原始会话信息。

### 6.5 usage 合并与全局去重

归一化 usage 只接受非负有限整数：`inputTokens`、`outputTokens`、`cacheReadTokens`。DeepSeek 推理 token 已包含在 output 口径中，不得再次相加；cache-write 在当前可观测数据中不可靠，不伪造。

同一 `(session, turn, step)` 可能先出现 usage chunk，最终 assistant message 又带累计/最终 usage：

- final assistant usage 替换该 step 的 chunk 累计快照，不与之相加；
- 只有没有 final 的 step 才使用最后一个可信 chunk；
- 重放相同 seq 或相同 messageId 必须幂等。

fork/子会话可能复制父会话 seed 消息。全局统计还需一层观察去重：

- 有 message ID 时使用本地 salt 的 `HMAC(messageId)`；
- 没有 ID 的 chunk-only 情况使用不含正文的确定性指纹，例如 session lineage、turn、step、seq 范围、usage 值和时间桶；
- 原始正文绝不能为去重而落盘；
- 父/子历史出现同一最终消息时全局只计一次，归属优先给原始/更早观察到的会话。

看板必须固定显示：“dsh 已观测用量，非账单”。会话标题生成、compaction 或不可见辅助调用可能没有完整事件，因此估算不能标为官方账单。

## 7. 持久化数据模型与 200ms 耐久边界

### 7.1 文件与写入方式

持久状态写入 Electron `userData/events-state.json`，而不是 `~/.dsh`。要求：

- schema versioned；未知未来版本 fail-closed 并保留原文件，不静默覆盖。
- 同目录临时文件写入、flush/close 后原子 rename；文件权限尽力设为 `0600`。
- 所有写入经单一串行队列，防止定时 flush 与 terminal flush 互相覆盖。
- 高频 usage 可 debounce；terminal 去重、waiting ledger、预算暂停等关键状态立即入队。
- 写失败只禁用依赖耐久性的副作用并在看板显示错误，不能用未持久状态继续制造重复通知。

### 7.2 建议 schema

```json
{
  "schemaVersion": 1,
  "contractId": "dsh-0.1.0-rc.6-events-v1",
  "salt": "local-random-base64",
  "updatedAt": "2026-08-15T00:00:00.000Z",
  "sessions": {
    "hmac-session-key": {
      "lastContiguousSeq": 0,
      "notificationFloorSeq": -1,
      "origin": "user",
      "openTurn": null,
      "lastTerminal": {
        "turn": 1,
        "seq": 10,
        "result": "completed",
        "at": "2026-08-15T00:00:00.000Z"
      },
      "lastNotifiedTerminalSeq": 10
    }
  },
  "notificationLedger": {
    "hmac-event-key": "2026-08-15T00:00:00.000Z"
  },
  "usage": {
    "days": [],
    "recentSamples": [],
    "dedupe": []
  },
  "tasks": [],
  "budget": {
    "pausedDate": null,
    "resumeDate": null,
    "crossingKey": null
  }
}
```

生产 schema 的限制：

- `sessions` 键为 HMAC 后的 session key，绝不存裸 ID。
- `notificationLedger` 只保留必要的 HMAC 键与时间，按 retention 清理。
- `usage.days` 保留日聚合；`recentSamples` 建议最多 14 天；任务摘要建议最多 100 条。
- 任务摘要只保留匿名任务键、时间、结果、token、估算费用、origin 和是否完整，不保留 title、消息正文、工具内容、cwd 或原始 frame。
- `salt` 只存在本机 WhaleDock userData，禁止上传。若丢失，旧 HMAC 状态视为不可关联并安全重建基线。
- pending approval/question 只需持久化已提醒键用于重启去重，不持久化问题内容。

### 7.3 副作用前持久化

为优先避免重复通知，terminal 流程固定为：

1. reducer 验证 seq 连续、terminal 已确认且高于首次基线。
2. 生成通知键并写入 `lastNotifiedTerminalSeq`/ledger 的候选状态。
3. 原子持久化成功。
4. 才调用系统 Notification 或降级链。

代价是第 3 步成功、第 4 步前崩溃可能漏一次通知；相反顺序会在重启后重复通知。本版本选择“少重复”并在文档说明该边界。

### 7.4 200ms 与 hard-crash 窗口

产品可以减少但不能消灭上游/本地进程的持久化竞态。建议 terminal 到达后：

- 不立即通知，等待至少约 300–400ms（大于需求中的 200ms 边界）；
- 在等待期间保持 WS 连续，并读取/确认 history 尾部已包含该 terminal；
- 再执行上述“本地持久化成功后通知”流程。

这能覆盖常见的 200ms 级上游落盘延迟，但不是事务证明。若 dsh 或机器在事件落盘前被硬杀，历史可能无法回放；若 WhaleDock 在 ledger 写入后、系统通知调用前被杀，可能漏报。README/操作手册和看板故障提示必须如实写成“尽力保证、存在极短 hard-crash 窗口”，不得宣称 exactly-once。

## 8. 通知与失败降级链

### 8.1 正常路径

主进程收到已持久化的通知意图后：

1. 若平台支持且应用有权限，使用 Electron `Notification`。
2. 点击通知只调用现有 `showApp()`，不得向 Harness DOM 注入跳转，也不得伪造精确定位到某个会话。
3. 查看通知/看板后清理 Dock badge 或托盘待办状态。

通知文案不包含用户问题、回答正文或会话 ID，只包含匿名任务标签和状态，例如“一个任务已完成”“有任务等待你确认”。

### 8.2 macOS/Windows 降级

系统通知不可用、被拒绝或抛错时依次尝试：

1. macOS Dock bounce（仅需要用户注意时，避免重复强提醒）；
2. Dock badge（例如 `1` 或 `!`）；
3. 托盘图标 tooltip/菜单状态，如“鲸坞 WhaleDock · 1 个任务等待处理”；
4. 用户恢复鲸坞时显示鲸坞自有 `notice.html` 小 banner。

Windows 没有 Dock 路径，直接降级到托盘状态与自有 banner。未签名 macOS/Windows 构建的系统通知、登录项和系统集成结果必须真机分别记录，不能用 smoke 代替。

`notice.html` 是独立、受控的 frameless child window：使用 `preload-notice.js` 暴露“显示主窗口/关闭”两个最小动作；不加载远程内容，不接受任意 HTML，不与 Harness renderer 通信。单个任务失败不得弹阻塞式 error dialog；持续故障统一在看板状态区呈现。

## 9. 设置、价格与费用估算

### 9.1 配置结构

在 `lib/config.js` 的 `DEFAULTS` 与现有 sanitize 体系中增加：

```js
taskNotifications: true,
budgetEnabled: false,
dailyTokenBudget: 1000000,
priceInputPerMillion: 1,
priceCacheReadPerMillion: 0.02,
priceOutputPerMillion: 2
```

以上默认值已由主代理于 2026-08-15 实时回读 [DeepSeek 官方中文价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)：本次侦察实际模型 `deepseek-v4-flash` 每百万 token 的缓存命中输入为 ¥0.02、缓存未命中输入为 ¥1、输出为 ¥2。设置页应显示“deepseek-v4-flash 官方默认价，核验于 2026-08-15，可自行修改”。若未来默认模型或官方价格变化，只能通过新版本/用户显式修改更新本地默认值；运行时绝不联网拉取价格。

价格由用户在设置页修改并本地保存。应用运行时不联网拉价，不增加新的出站请求。三个字段均为每百万 token 的本地货币金额；输入必须为有限、非负并设置合理上限和小数位，非法值回退到已验证默认值或“未配置”。

### 9.2 费用公式

```text
estimatedCost =
  (inputTokens * priceInputPerMillion
   + cacheReadTokens * priceCacheReadPerMillion
   + outputTokens * priceOutputPerMillion) / 1,000,000
```

费用结果始终标“估算”；当任何对应价格未配置或 usage 覆盖存在 gap 时，不显示伪精确总额，而显示“暂不可估算/数据不完整”。

## 10. 每日预算软熔断

每日预算按本机当前时区自然日和已观测总 token 计算。用 clock/timezone 注入测试 DST、跨日与周一周界。它是事后软熔断，不是供应商额度：可能在一个 step 完成后才发现超额，不能追回已花 token，也不能保证在下一次上游调用前绝对阻止。

规则：

1. `budgetEnabled:false` 时只统计，不停止。
2. 首次从未超额跨到 `todayTokens >= dailyTokenBudget` 时生成一次 `budget-crossed`。
3. 主进程重新核验当前 backend identity/generation 以及 `spawnedByUs === true` 后，才调用现有受控 stop 流程清理自己拉起的进程树。
4. attach 到外部服务时绝不 stop；只通知“已达到预算，当前服务不是鲸坞启动，未自动停止”。
5. 将 `pausedDate` 和 crossing key 原子持久化，阻止自动恢复、启动自愈或 backend 意外退出重启绕过预算。
6. 看板提供一次明确的“今日继续运行”动作。确认后写入同日 `resumeDate`，再由主进程显式重启；当天不再自动 stop，但继续统计并显示超额。
7. 本机日期进入下一自然日后清理前一日暂停/恢复状态，重新按新日预算判断。

预算判断不得从 renderer 传入的 token 总数执行；renderer 只能请求动作，主进程使用自己的规范状态再次校验。

## 11. 看板窗口、preload 与 IPC

### 11.1 窗口

新增 `dashboard.html` 和 `preload-dashboard.js`，由独立 `BrowserWindow` 加载本地文件：

- `contextIsolation:true`
- `nodeIntegration:false`
- 禁止导航、弹窗和新窗口；外链如未来存在必须由主进程白名单处理，本版不需要。
- CSP 只允许本地脚本/样式和必要的 data image；优先不使用 inline script。
- 主窗口保持无 preload，不能为了看板复用而改变 Harness 安全边界。

看板最小内容：事件能力/覆盖状态、今日与本周 token、估算费用、顶层/子代理聚合、最近匿名任务、当前预算状态、价格口径、错误降级提示。tooltip 可显示 `鲸坞 WhaleDock · 今日 12,345 tokens`。

### 11.2 最小 IPC 合约

renderer -> main：

- `dashboard:get`：读取规范化快照。
- `dashboard:export-report`：传入 taskKey、主题和 `copy|save` 动作；不接受 renderer 自报的 totals。
- `dashboard:resume-budget`：请求今日继续，主进程复核状态。
- `dashboard:show-main`：显示主窗口。

main -> renderer：

- `dashboard:state`：推送新的只读快照。

所有 handler 必须校验：

- sender 是当前保存的 dashboard webContents；
- `event.senderFrame === event.sender.mainFrame`；
- URL 是打包内预期 `file:` 页面；
- 参数是长度/枚举受限的 plain object。

preload 只通过 `contextBridge` 暴露上述窄 API，并返回取消订阅函数；不暴露 `ipcRenderer`、路径、shell、fs 或通用 invoke。快照经过主进程 sanitize，仅含 availability/coverage、日周聚合、匿名 session/task 行、预算与价格；不含原始 ID、frame、正文、工具数据或 cwd。

现有设置窗口可复用已建立的可信 sender 校验、context isolation 和配置 save/read 模式。`preload-settings.js` 若现有通道已足够则不新增能力；不要为了方便把看板通用 API 塞进设置 preload。

## 12. 离屏战报卡片

生产用 `report-card.html` 可参考现有深色/浅色设计原型，但必须成为独立、可测试、安全的打包资源。流程：

1. 看板仅传 `taskKey`、白名单主题 `dark|light` 和动作 `copy|save`。
2. 主进程用 taskKey 从规范数据仓重新读取任务摘要与统计，忽略 renderer 提供的任何显示数值。
3. 创建隐藏 `BrowserWindow`，建议固定 1080×1440、`show:false`、`contextIsolation:true`、`nodeIntegration:false`，加载 `report-card.html` 与专用 `preload-report.js`。
4. 通过一次性 IPC 传递经 schema 校验的纯数据。renderer 只用 `textContent` 和属性白名单填充，禁止把标题或状态插入 `innerHTML`。
5. 等待 `document.fonts.ready` 与至少两次 `requestAnimationFrame`；若内容高度超过画布，按固定规则裁剪/缩放而非任意扩窗。
6. `capturePage()` 得到 PNG；`copy` 使用 `clipboard.writeImage`，`save` 经用户选择的 save dialog 再写文件。
7. 无论成功失败都在 `finally` 销毁离屏窗口并移除一次性 listener。

任务标题原则上不持久化。若当前内存中存在经长度和控制字符清理的标题，可临时用于卡片；否则使用“任务 01”之类匿名标签。图片中固定标注“dsh 已观测用量，非账单”。主题、尺寸、字段缺失与恶意长文本均需 fixture；视觉是否合格仍需人工查看实际 PNG，不能由 smoke 代替。

## 13. 安全、隐私与故障策略

### 13.1 安全清单

- 只连接当前 backend 的 loopback 地址；不接受 renderer 提供 endpoint。
- HTTP/WS 请求、响应、frame、数组长度、字符串长度、数字范围均设上限。
- WS 不发送消息；HTTP 只允许 describe/list/history 三个方法。
- 日志只记状态码、能力状态、匿名 HMAC 后短键与结构错误，不记 raw payload/session ID。
- 新窗口统一本地 `file:`、隔离上下文、无 Node、CSP、禁止导航/弹窗。
- 所有 renderer 输入为不可信；副作用由 main 依据规范状态重算。
- HMAC salt 与状态只保留在 WhaleDock userData；无遥测、无同步。
- 不读写 `~/.dsh`；历史数据通过 dsh 正式只读 API 获取。

### 13.2 fail-closed / fail-open 边界

- 协议、版本、连续性、持久化去重失败：事件副作用 fail-closed，停通知/预算停止/战报中的相关数据。
- 主 Harness 体验：fail-open，主窗口继续可用，backend 基础生命周期不因附加事件功能被阻断。
- 价格缺失：token 可显示，费用 fail-closed 为未配置。
- 系统通知失败：降级到 Dock/tray/banner，不反向撤销已持久 ledger。
- 看板 renderer 崩溃：可重新创建并从 main 快照恢复，不影响 backend。
- 战报 capture/save 失败：销毁临时窗口并报告可操作错误，不修改 task/usage 状态。
- 状态文件损坏：保留原文件为用户可诊断副本或原路径旁的有界备份，建立新基线；不把旧任务重新通知。
