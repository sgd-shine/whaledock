## 一、总体结论（30 秒版）

这次交付的质量是高的，而且不只是"代码能跑"那种高：分层干净、有 12 项自动化测试、有 CI 自动打包发布、有完整的文档和决策记录、安全配置全部做对、合规（非官方定位、原创图标）也处理到位。我核实了线上状态：GitHub 仓库 `sgd-shine/harness-desktop` 已公开，`v0.1.0` Release 由 GitHub Actions 于今天自动构建发布，安装包资产齐全。以一个 v0.1 桌面壳应用的标准看，这是**优秀**的工程交付。

短板不在代码，在产品层面：一是有几个边角小 bug 和"上游版本漂移"风险（下文有清单，半天能修完）；二是竞争环境比预想的激烈——Harness 开源才两天，社区已经冒出至少 5 个桌面客户端，其中最强的一个已做到"免装 Node、三平台、自动更新"。所以接下来的开发方向，建议往**差异化（宠物、个性化界面）+ 快速补齐 Windows** 走，这恰好和你自己的想法一致，而且宠物这个点目前全生态没人做。

## 二、它到底是怎么实现的（通俗版，先纠正一个理解）

你说它是"做了一个 APP 的镜像，实时投射网页端的操作界面"——**方向对了一半，但"投射/镜像"这个词不准确**，准确的理解分三层：

**第一，那个"网页端"根本不在云端，就在你电脑里。** Harness 官方的用法是：在终端敲 `npx @deepseek-ai/dsh web`，你电脑上就启动了一个小型本地服务（术语叫后端），它在本机的 3080 端口"开门营业"；然后你用浏览器访问 `127.0.0.1:3080`（这个地址永远指向你自己的电脑）看到界面。所以不存在"远方有个网页被投射过来"——发动机和仪表盘都在你本地。

**第二，App 不是"镜像"别处的画面，它自己就是那个浏览器。** Electron 的本质是"一个被拆掉地址栏、皮肤可定制的 Chrome"。Harness Desktop 的主窗口就是用这个内置浏览器**直接打开** `127.0.0.1:3080`，和你自己开 Chrome 访问是同一份界面、同一个网络请求——不是截图、不是投屏、没有中转，所以也没有任何"实时同步"的开销。真正的界面还是官方 Web UI，我们没有重写它。

**第三（这才是这个 App 的真正价值），代码的九成都花在"当保姆"上。** 打开 `main.js` 和 `lib/backend.js` 你会发现，绝大部分逻辑都在干这些事：

1. **先敲门再开工**：启动时先探测 3080 端口是否已有服务。有（比如你自己在终端跑了）→ 直接接入，退出时也不杀它；没有 → 自动帮你把 `dsh` 拉起来。
2. **找得到 Node**：macOS 有个经典大坑——双击图标启动的 App 拿不到你终端里的 PATH，Homebrew/nvm 装的 Node 全都"看不见"。它会主动去问登录 shell、扫常见安装目录（连你机器上 Hermes 装的 Node 都找到了）。这是这类应用最容易翻车的地方，它处理得很好。
3. **等它就绪、给你直播**：首次启动 npx 要下载组件（可能几分钟），启动页会实时滚动后端日志，失败了能一键复制日志、重试。
4. **退出时打扫干净**：dsh 启动后其实是一棵进程树（npx → dsh → 子进程），退出时对整个进程组先礼后兵（SIGTERM，4 秒后 SIGKILL），不留"孤儿进程"占着端口。
5. **桌面化的糖**：托盘常驻、关窗不退出、⌘⇧H 全局呼出、窗口位置记忆、外链跳系统浏览器、中文菜单。

一句话总结：**发动机（dsh）是 DeepSeek 的，驾驶舱玻璃（Web UI）是 DeepSeek 的，这个 App 做的是整辆车的底盘、点火系统和车门——把"开终端敲命令 + 浏览器找标签页"变成"双击一个图标"。**

## 三、审计发现

### 3.1 做得好的（值得保持的工程纪律）

**分层与可测试性**：`lib/` 三个核心模块（进程管理/配置/日志）刻意不依赖 Electron，用纯 Node 就能测，12 项冒烟测试覆盖了"启动假后端→端口就绪→杀进程组→端口关闭"完整生命周期。**零运行时依赖**：除 Electron 本身外不引入任何第三方包，供应链风险约等于零，也没有任何遥测上报。**安全姿势正确**：渲染层开启 contextIsolation、关闭 nodeIntegration，主窗口连 preload 都没有，外部链接一律踢给系统浏览器——这几项是 Electron 应用最常见的安全失分点，它全对。**协作流水线可复现**：开发方案 → AGENTS 约束 → Codex 真机执行 → DECISIONS/STATE/HANDOFF 记录，这套"AI 接力"流程本身就是资产，后续每个新功能都能复用。

### 3.2 值得优化的问题清单

按"建议处理顺序"排列，前五项加起来约半天 agent 工作量，可以打包成 v0.1.1：

| # | 问题 | 通俗解释 | 修法方向 |
|---|------|---------|---------|
| 1 | **上游版本漂移（最大风险）** | 启动命令 `npx -y @deepseek-ai/dsh` 永远拉**最新版**。上游还是 rc 阶段、明说会有破坏性变更——哪天上游改了端口或子命令，所有用户的 App 一夜变砖 | 默认锁定已验证版本（如 `@0.1.0-rc.6`），配置文件留升级开关；启动页显示当前后端版本 |
| 2 | **超时后点"重试"会双开进程** | 首启下载超过 5 分钟报超时，此时第一个 dsh 其实还活着；点重试会再拉起第二个，两者抢端口；且此后退出时可能漏杀自己拉起的进程（内部标记被误翻转） | 重试前先停掉旧进程再拉新；接入前判断端口是否是自己的子进程开的 |
| 3 | **重试时不刷新 PATH 缓存** | 报"找不到 Node"后用户现装 Node，点重试可能仍找不到（目录清单被缓存了，nvm 新装目录不在里面），与错误提示承诺的流程矛盾 | 重试时强制 `fullPath(true)` 重新探测 |
| 4 | **页面加载重试不区分主框架** | `did-fail-load` 没检查 `isMainFrame` 和 `ERR_ABORTED`——界面里一个小 iframe 加载失败也可能触发整窗重载 | 只对主框架、非 ABORTED 错误重试 |
| 5 | **后端悄悄挂掉时的静默失败** | 窗口收在托盘里时后端崩了，不弹任何提示；下次呼出看到的是坏页面 | 挂掉即自动重启（带退避上限），或发系统通知 |
| 6 | 接入模式下"重启后端"是空操作 | 接入你终端里服务时点"重启后端"，实际只是重连了一下 | 菜单项按模式改名/置灰，避免误解 |
| 7 | 端口误认 | 3080 被无关服务占用时会被误当成 Harness 直接接入（方案里已知） | 接入前发一个 HTTP 请求验证特征 |
| 8 | 日志轮转只在启动时检查 | 长期挂着不重启，日志可超 5MB 上限 | 写入时也定期检查 |
| 9 | 无设置界面 | 改端口/快捷键/自启动都要手编 JSON | 做个小设置窗（也是好视频素材） |
| 10 | CI 只在打 tag 时跑测试 | 平时改动推上去没人拦 | 加 push/PR 触发的冒烟 workflow（纯 Node，用便宜的 ubuntu runner 即可） |
| 11 | 只有 Apple Silicon 版 | Intel Mac 用户装不了 | electron-builder 加 x64/universal 目标即可 |
| 12 | 未签名的摩擦 | 首次要"右键→打开"，且 macOS 上**不签名就没法做真正的自动更新**（electron-updater 硬性要求） | $99/年 Apple 开发者账号做签名公证，一次解决两个问题（可放 v0.3+） |

## 四、接下来开发什么：三个想法的实现方案

### 4.1 桌面宠物（推荐第一个做：全生态没人做，且是天然视频素材）

**思路**：不碰官方 Web UI，做一个独立的透明无边框小窗——一只常驻桌面角落（或跟随主窗口）的小生物，**它的状态实时反映 Harness 引擎的状态**。这不只是装饰：它同时解决了"任务跑完了我却不知道"的真实痛点（宠物庆祝 = 任务完成通知）。

**状态设计（宠物 = 引擎的表情包）**：启动中→伸懒腰；首次下载组件→吭哧吭哧搬箱子；就绪空闲→打盹；任务进行中（日志滚动频繁）→奋力打字；任务完成（日志安静下来）→跳舞庆祝+可选系统通知；后端挂了→晕倒举个"救我"的牌子，点它一键重启。

**为什么现在做很便宜**：App **已经**在逐行解析 dsh 的日志流（启动页直播用的就是它），后端生命周期状态机也是现成的——宠物只是给这些已有事件配上动画。技术上就是再开一个小 BrowserWindow（透明、置顶、可拖动、点击切换主窗显隐），动画先用 CSS/像素 sprite（原创形象，顺便成为项目吉祥物和品牌记忆点），以后可升级 Lottie。预计给 Codex 一天工作量。进阶版（v2）可以接上游的 headless/JSON-RPC 接口拿真正的任务级事件，宠物就能区分"在写代码"和"在搜网页"。

### 4.2 界面定制（四层阶梯，由浅入深随时停）

**第 0 层（已经完全自主）**：启动页、图标、托盘、宠物、设置窗都是自己的代码，随便改，零风险。

**第 1 层：CSS 注入换肤（推荐 v0.2 做）**。Electron 可以在页面加载完后把一段 CSS"塞进"官方界面（`insertCSS`），等于给网页穿衣服：改配色、圆角、字体、隐藏元素都行。做成主题包机制——`themes/` 文件夹放多个 `.css`，菜单"视图→外观"切换、跟随系统深浅色。风险仅是上游改版后某些样式失效，但失效也不影响功能。一天工作量，且"一键换肤"演示效果极好。

**第 2 层：fork 官方 Web UI**。查证过：Harness 的界面本身就是个独立 MIT 开源 npm 包（`@deepseek-ai/dsh-web-app`），可以 fork 下来深度改造再让 App 加载自己的版本（TinyWhale 就是这条路）。自由度大增，代价是每次上游发 rc 都要跟着合并，维护成本高。建议等上游出 1.0 稳定版再考虑。

**第 3 层：基于 JSON-RPC 自研原生界面**。完全脱离官方 UI，周级工作量，是"远期梦想"选项（开发方案里也这么定位）。

### 4.3 Windows 版（可行性已确认，工作量比想象小）

**先回答"能不能"：能。** dsh 是纯 Node 命令行程序，npm 包没有声明操作系统限制，社区已有 Windows 安装教程，且多个竞品已在 Windows 跑通——后端没问题，要改的只是我们这层壳。

需要动的四处（当初写代码时已留了口子，比如进程分组那行已按平台做了分支）：

1. **找命令**：Windows 上可执行文件叫 `dsh.cmd`/`npx.cmd`，探测目录换成 `%APPDATA%\npm`、nvm-windows、Program Files 等；macOS 那套"问登录 shell 要 PATH"在 Windows 上反而不需要（GUI 程序本来就继承系统 PATH）。
2. **杀进程树**：`process.kill(-pid)` 是 Unix 专利，Windows 用 `taskkill /pid X /T /F`。
3. **托盘图标**：mac 的黑白模板图换成 Windows 的彩色 `.ico`；快捷键 `CommandOrControl` 会自动映射成 Ctrl，不用改。
4. **打包与 CI**：package.json 加 `win` 目标（NSIS 安装器 + 便携版 zip），GitHub Actions 加一个 windows runner——以后每次打 tag，mac 和 Windows 安装包同时自动发布。

预计给 Codex 一天（外加真机验证：你需要一台 Windows 电脑，或借 CI 构建 + 找朋友实测）。注意事项：未签名的 exe 首次运行会遇到 SmartScreen 提示（"更多信息→仍要运行"），README 写清楚即可，和 mac 右键打开是同类问题。顺手福利：electron-builder 再加一行还能出 Linux AppImage。

### 4.4 "确保不同的人都能装上"（分发清单）

按性价比排序：**①** 提交 awesome 榜单收录（零成本曝光）；**②** README 补截图/演示 GIF（STATE 里的待办，直接影响转化）；**③** Windows 版 + Intel Mac 版（覆盖面翻倍）；**④** 发布到 winget（Windows 包管理器，免费）和自建 Homebrew tap（`brew install --cask`，开发者群体喜欢）；**⑤** 免装 Node——这是竞品的杀手锏，但我们有个巧办法：**Electron 自带完整 Node 运行时**（`ELECTRON_RUN_AS_NODE` 模式可以把 App 自己当 Node 用），配合把 dsh 预打包进安装包，就能做到"下载即用"而几乎不增加体积，2-3 天工作量，建议放 v0.4；**⑥** Apple 签名公证 $99/年，消除"右键打开"门槛并解锁 mac 自动更新，等有一定用户量再上。
